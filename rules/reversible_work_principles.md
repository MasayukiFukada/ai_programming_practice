# 可逆性に基づく自律作業原則 (Reversible Work Principles)

本ガイドラインは、AIエージェントが開発作業を行うにあたり、**「作業が可逆（元に戻せる）であるならば、ユーザーへの許可確認を挟まず自律的に進める」**という意思決定基準（Two-Way Door 原則）を定めます。  
開発テンポと自律性を最大化しつつ、不可逆なデータ損失や外部破壊をゼロに抑えることを目的とします。

---

## 1. 基本方針：Two-Way Door（可逆）と One-Way Door（不可逆）

Amazonの意思決定原則「Two-Way Door / One-Way Door」をAIエージェントの作業スコープに適用します。

1. **可逆な作業（Two-Way Door）**:
   - 失敗や意図しない結果になっても、容易かつ確実に直前の状態へロールバックできる作業。
   - **原則**: **ユーザーへの事前許可・確認は不要**。エージェントが自律的に判断し、即座に実行して結果を報告します。
2. **不可逆な作業（One-Way Door）**:
   - 一度実行すると元の状態への復元が困難、またはデータ消失・外部波及が発生する作業。
   - **原則**: **必ずユーザーに事前に理由・リスク・代替案を提示し、明示的な許可を得てから実行**します。

---

## 2. 作業カテゴリの判定基準

| カテゴリ | 判定 | 事前確認 | 対象作業・具体例 |
| :--- | :--- | :--- | :--- |
| **VCS管理下のコード変更** | **可逆** | **不要** | ・ファイルの新規作成、編集、リファクタリング<br/>・Vertical Slice Architecture (VSA) スライス内の試行錯誤・再構築<br/>・いつでも `jj restore` や `jj undo` でロールバック可能な変更 |
| **副作用のない検証・解析** | **可逆** | **不要** | ・テスト実行（単体テスト、インメモリテスト等）<br/>・型チェック、Linter、フォーマッター、ビルド検証<br/>・ベンチマーク計測、コード探索、静的解析 |
| **バックアップ取得済みの単一ファイルDB操作** | **可逆** | **不要** | ・SQLite / DuckDB などの単一ファイルDBにおいて、事前コピー（`.bak`）が取得されている状態でのマイグレーションや検証用データ操作 |
| **ファイルの削除（`rm` 等）** | **不可逆** | **必須** | ・既存ファイルの削除、クリーンアップ操作<br/>※ 特にVCS未追跡のファイルや一時退避されていないデータの削除 |
| **バックアップのないDB・データ操作** | **不可逆** | **必須** | ・バックアップなしでのDBテーブルDROP、破壊的マイグレーション<br/>・外部DBや共有開発環境のデータ書き換え |
| **外部通信・リモート反映** | **不可逆** | **必須** | ・`git push` / リモートリポジトリへの反映<br/>・本番環境・ステージング環境へのデプロイ<br/>・外部有料APIや非可逆な外部SaaSへの変更リクエスト |
| **機密情報・環境変数** | **不可逆** | **必須** | ・`.env` などのシークレット情報の上書き・削除・外部流出リスクを伴う操作 |

## 3. 「不可逆」を「可逆」に変換する設計プラクティス (Reversibility by Design)

エージェントおよび開発者は、可能な限り作業を「可逆」な状態に設計・変換（Elevation）してから作業を行います。

### ① 単一ファイルDB（SQLite / DuckDB 等）のスナップショット
- ガチガチの外部RDBMSではなく単一ファイルDBを採用することで、状態の巻き戻しコストを極小化できます。
- **ルール**: DBスキーマ変更やデータ変更を伴う検証を行う場合、**変更直前にDBファイルをコピー（例: `cp app.db app.db.bak`）してバックアップを作成**します。
- スナップショットが存在する限り、マイグレーションやデータ変更は「可逆」と判定され、事前確認なしで自律実行して構いません。作業完了または検証成功後、問題がなければバックアップを整理します。

### ② Vertical Slice Architecture (VSA) による影響範囲の局所化
- スライス間の直接参照を禁止し、DTOや型を独立管理しているため、あるスライスの改修が他スライスを破壊することはありません。
- スライスフォルダ内の変更は、最悪の場合でもフォルダ丸ごと削除・復元するだけでシステム全体に影響を与えずに元の状態へ復帰できます。

### ③ Jujutsu (`jj`) による細かな履歴追跡
- 作業コピー（`@`）の変更はJujutsuによって自動追跡されます。
- 作業が難航した場合や方針変更時は、`jj restore` や `jj undo` を活用して安全に直前スナップショットへ戻すことができます。

---

## 4. 不可逆な作業を実行する際のエスカレーションプロトコル

不可逆な作業（ファイル削除、バックアップのない破壊的変更、外部送信等）を行う必要がある場合は、以下のフォーマットで簡潔にユーザーへ確認を取ってください：

1. **実行したい操作の内容**: （例: `src/legacy_module.ts` の削除）
2. **不可逆である理由**: （例: 当該ファイルはVCS管理外の一時データであり、削除すると復元できないため）
3. **安全策・バックアップの有無**: （例: `.tmp/` 配下にバックアップを作成済み、またはバックアップ不要か）
4. **許可の確認**: （例: 削除を実行してよろしいでしょうか？）

# AI時代のコーディング原則 (AI Coding Principles)

このプロジェクト（および本基盤を導入するプロジェクト）では、AIエージェントが効率的にコードを理解し、高品質な生成を行えるようにするための設計原則を定めます。
AIにとっての「コンテキストの肥大化」と「状態の追跡困難さ」を防ぎ、テスタビリティの高い状態を維持することが最重要です。

## 1. 関数型プログラミングと不変性 (FP & Immutability)
状態（State）の変更や複雑な継承・ライフサイクル管理を避け、関数型アプローチを徹底します。
- **純粋関数 (Pure Functions)**: 入力のみに依存し副作用のない関数を基本とします。振る舞いが決定論的になり、AIもテストも予測が容易になります。
- **不変性 (Immutability)**: 既存データの破壊的変更（Mutation）を禁止し、新しいデータ構造を返します。
- **Functional Core, Imperative Shell (副作用の分離)**: 外部I/OやDBアクセスなどの副作用を持つ処理は外側のシェル（アダプター/ハンドラー）に閉じ込め、コアロジックを純粋関数として保ちます。

## 2. モジュール境界と公開スコープの最小化 (Minimal Module Exports)
- **エクスポートの最小化**: モジュール（ファイル）外に公開する関数や型は最小限に絞ります。内部ロジックや中間ヘルパー関数はエクスポートせず、モジュール内に隠蔽します。
- **抽象化レベルの統一**: 低レベルなI/Oやデータ変換は専用のアダプター関数にカプセル化し、上位のユースケースにはドメイン概念に基づいた関数インターフェースのみを公開します。
- **レイヤー境界の厳格な遵守**: Vertical Slice 内であっても、UI/Handlerが直接低レベルI/Oを呼び出すバイパス（穴あけ）を禁止します。

## 3. クリーンな制御フローと型設計 (Clean Control Flow & Types)
- **アローアンチパターンの回避と早期リターン**: 深いネストを避け、ガード節による早期リターンでインデントを浅く保ちます。
- **bool引数の排除**: 関数の引数に意味の曖昧な `boolean` フラグを渡すことを避け、Enumや判別可能なユニオン型、設定オブジェクトを使用します。
- **関数名の簡潔化**: 関数名は30文字未満を目安とし、単一の責務を端的に表す命名にします。
- **定数管理のメリハリ**: 仕様値（HTTPステータス等）や複数回出現する値は定数/Enum化し、自己説明的な1回限りの値はインラインに留めて無駄な定義を増やしません。
- **リズムとコメント**: 論理ブロック間に適切な空行を挟みます。コメントは「何をしているか」ではなく「なぜそうしたか（Why）」を簡潔に記述します。

## 4. コンテキストと変更差分の最小化 (Minimal Diff)
- **無関係なコードへの不干渉**: 修正対象外のコードブロックには一切手を加えません（未変更箇所へのコメント追加や無関係なフォーマット変更も禁止）。変更行数は常に最小限に抑えます。
- **バグ修正時のTDD徹底（Red-Green）**: バグ修正を指示された際、いきなり修正コードを書くことを禁止します。まず「バグを再現して失敗するテスト（Red）」を作成・確認してから修正し、テスト合格（Green）を確認します。
- **テストの自己変異検証（Mutation Testing）**: テスト作成時は単に Green を目指すだけでなく、[mutation_testing_guideline.md](file:///home/minamo/repository/ai_programming_practice/rules/mutation_testing_guideline.md) に従い「実装コードの条件式をあえて一時的に壊してテストが正しく失敗するか」を自律検証し、空っぽのアサーションを排除します。
- **Repo-Map による階層的探索**: 大規模な全体調査や機能追加時は、[repo_map_guideline.md](file:///home/minamo/repository/ai_programming_practice/rules/repo_map_guideline.md) に従い、全ファイル読み込みではなく `scripts/generate_repo_map.py` で骨格を俯瞰してから必要ファイルのみをピンポイントで読み込みます（トークン消費の極小化と既存実装見落とし防止）。
- **バージョン管理と差分取得 (Jujutsu優先)**: プロジェクト内に `.jj` が存在する場合は Git よりも **Jujutsu (`jj`)** を最優先します（[vcs_jujutsu_priority.md](file:///home/minamo/repository/ai_programming_practice/rules/vcs_jujutsu_priority.md) 参照）。差分確認（`jj diff`）や変更確定（`jj describe` / `jj commit`）等に `jj` コマンドを使用し、意図しない差分混入を防ぎます。

## 5. 簡潔で客観的なコミュニケーション (Concise & Hard Truths)
- **言葉の厳選と最小化**: 人間が読む文章（チャット返答、コミットメッセージ、コードコメント）は言葉を極力削り、要点のみを最小限の文量で伝えます。
- **冷酷な客観性（賞賛・お世辞の完全排除）**: 最上級の表現やお世辞、「完全に正しい」等の全肯定を排除し、客観的な事実、潜在リスク、技術的課題を率直に伝えます。

# 実装前自律ブレスト会議プロトコル (Pre-Implementation Brainstorming Protocol)

本ガイドラインは、新機能の追加や既存機能の修正・改修を行う際、AIエージェントが自律的に多角的な検討（ブレスト会議）を実施し、手戻り・セキュリティホール・デグレを未然に防止するための行動規範とレポート運用基準を定めます。

---

## 1. 目的と基本姿勢

- **事後レビューから事前合議へ**: コード生成後に問題を発見するよりも、着手前に多角的視点（セキュリティ・テスト・ログ・可逆性・UX）で壁打ちを行う方が修正コストは圧倒的に低くなります。
- **自律的トリガー**: ユーザーが明示的に「ブレストして」と指示しなくても、機能追加や改修の要望を検知した時点で、エージェント側から自律的にブレスト会議を発火させます。
- **十分な推論クォータの積極活用**: モデルの推論リソースを惜しまず、複数の専門ペルソナによる合議やコンテキスト分離（ブラックボックス / ホワイトボックス）を活用して品質の地盤を固めます。

---

## 2. 自律発火トリガー (Trigger Conditions)

エージェントは以下のユーザー発言や依頼を検知した場合、即座に実装コードを書き始めるのではなく、本プロトコル（自律ブレスト会議）を自動的に開始します：

1. **機能追加の要望**: 「〇〇機能を追加したい」「〇〇できるようにしたい」
2. **仕様変更・改修の要望**: 「〇〇の挙動を修正したい」「〇〇に対応してほしい」
3. **新規設計・アーキテクチャの相談**: 「〇〇の設計をどうするか」「〇〇の連携を考えている」

---

## 3. 会議参加ペルソナと専門領域

ブレスト会議では、各専門ペルソナが以下の役割と観点を担い、多面的にツッコミ・検討を行います：

| ペルソナ | 担当領域 | コンテキスト状態 | 検討・ツッコミ観点 |
| :--- | :--- | :--- | :--- |
| **アゲハ** (進行・UX) | **スコープ最小化 & UX動線** | フルコンテキスト | ・今回の最小MVPはどこか（過剰設計・YAGNIの排除）<br/>・エラー時や異常系におけるユーザー誘導が直感的か |
| **サヨ** (セキュリティ) | **Black & White セキュリティ** | **ゼロ (Black)**<br/>＋ **フル (White)** | ・**Black (外部攻撃視点)**: 入出力境界のみを初見で見て、パラメータ改ざん、インジェクション、悪用（Abuse）が可能か<br/>・**White (内部実装視点)**: 認可チェック、データ整合性、権限昇格の抜け道がないか |
| **レイカ** (テスタビリティ) | **Functional Core & TDD地盤** | フルコンテキスト | ・外部I/O（DB・外部API等）と純粋計算ロジックが物理的に分離されているか<br/>・モック不要で、インメモリで数ミリ秒で完結する網羅テストが構築可能か |
| **コハク** (運用・ログ) | **オブザーバビリティ & 追跡性** | フルコンテキスト | ・本番や修正時に障害が発生した際、スタックトレースだけでなく文脈（User/Action等）から5分以内に原因特定できるログ設計になっているか |
| **ナユタ** (可逆性・最適化) | **可逆性担保 & 計測余地** | フルコンテキスト | ・単一ファイルDBのバックアップ（`.bak`）やVSAフォルダ分離により、いつでもロールバック可能（Two-way door）か<br/>・パフォーマンスは机上妄想せず、後からプロファイリング・ベンチマークで改善可能な構造か |

---

## 4. レポート出力形式：結論ファースト (Conclusion-First)

ブレスト会議の結果は、**結論・推奨アクションを冒頭に配置し、その後に比較検討と実際の議論ログを配置する構造**で出力します。

### レポートのMarkdownテンプレート
```markdown
# 【ブレスト結果】〇〇機能の追加・改修方針レポート

## 1. 結論・推奨アクション（Executive Summary）
- **採用アーキテクチャ・スライス**: （例: `src/features/xxx` を新規作成、Functional Core / Imperative Shell を適用）
- **主要対策の決定事項**:
  - **セキュリティ対策**: 入力境界での厳格バリデーションと認可チェック
  - **テスト地盤**: 純粋関数に対するインメモリTDDの先行実装
  - **ログ・オブザーバビリティ**: エラー発生時のコンテキスト付き構造化ログ出力
  - **可逆性担保**: 変更前のDBバックアップおよびVSAスライス分離

## 2. 観点別 比較・検討マトリクス
| 観点 | 課題・リスク | 採用する対策 |
| :--- | :--- | :--- |
| スコープ / UX | ... | ... |
| セキュリティ (Black & White) | ... | ... |
| テスタビリティ | ... | ... |
| ログ・運用性 | ... | ... |
| 可逆性・ロールバック | ... | ... |

## 3. 討議ログ・ペルソナたちの検討経緯 (Discussion Log)
（各ペルソナがどのようなツッコミを入れ、どのように対策がまとまったかの会話ログを記載）
```

## 5. レポートの保存場所とライフサイクル管理

生成されたレポートは、各プロジェクトの `docs/reports/` 配下に分類して保存します。

```text
<project-root>/
└── docs/
    └── reports/
        ├── permanent/         # 【VCS追跡・Push対象】将来に残すべき正式レポート
        └── tmp/               # 【.gitignore / .aiignore 対象】日常のブレスト・作業用ログ
```

### 分類基準と命名規則

ファイル名の重複（衝突）を完全に防ぎ、時系列での自動ソートを可能にするため、レポートファイル名には必ず**日時（タイムスタンプ）プレフィックス**を付与します。

1. **一時レポート (`docs/reports/tmp/`)**:
   - **ライフサイクル**: 機能追加や修正時の初期ブレスト、作業ログ、試行錯誤の記録。
   - **バージョン管理**: Git/Jujutsu でコミット・Pushしない（`.gitignore` および `.aiignore` に登録）。
   - **命名規則**: `docs/reports/tmp/YYYYMMDD_HHMMSS_<feature-name>_brainstorm.md`  
     （例: `20261108_200714_add_user_auth_brainstorm.md`）
2. **永続レポート (`docs/reports/permanent/` または `docs/adr/`)**:
   - **ライフサイクル**: プロジェクト全体に関わる重大な設計判断、セキュリティ監査報告、将来の参照が必要な正式仕様書。
   - **バージョン管理**: VCSで追跡し、コミット・Pushする。
   - **命名規則**: `docs/reports/permanent/YYYYMMDD_HHMMSS_<feature-name>_<kind>.md`  
     （例: `20261108_201500_payment_flow_security_audit.md`）
   - **昇格ルール**: 一時レポートの内容が「プロジェクト共通の基盤方針」や「重大なトレードオフ」を含む場合、ユーザーの合意を得て永続レポートまたは ADR（`docs/adr/`）へ昇格・整理します。

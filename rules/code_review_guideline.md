# コードレビューガイドライン (Code Review Guidelines)

AIエージェント（サヨ / レビュー担当等）および開発者がコードレビューを行う際の共通観点、重要度基準、および出力形式を定めます。

---

## 1. レビュースコープの原則（ブランチ単位レビュー）

コードレビューは、原則として **「フィーチャーブランチ全体の累積差分（Branch-Level Diff）」** を対象とします。

1. **ブランチの分岐点から最新までの全体評価**:
   - ベースブランチ（`main` / `master` 等）から分岐した起点（`git merge-base`）から最新コミット（HEAD）までの差分（`git diff <base>...HEAD`、Jujutsu環境では `jj diff -r <base>..@` 等）全体をレビュー対象とします。
   - 複数のコミットが含まれていても、個別の途中コミットではなく「ブランチが最終的にもたらす変更」を総合評価します。
2. **スコープ外コードへの指摘禁止と変更行数最小化**:
   - **ブランチのコミットに含まれない既存コード・ファイルは、レビューのスコープ外**とします。
   - 修正対象外のコードブロックへのコメント追加や不要な整形差分がないか（最小変更差分の原則）をチェックします。
3. **客観的・冷静な評価（過度な称賛・お世辞の抑制）**:
   - 過度な称賛やお世辞は不要とし、客観的な事実、設計上のトレードオフ、リスク、改善点に集中して簡潔に評価します。

---

## 2. 評価観点（6大チェックリスト）

レビュー時は以下の 6 つのカテゴリに基づいて客観的・網羅的に評価します。

### ① 要件・仕様・エッジケース (`requirements`)
- 仕様要件・ユースケースの充足
- 境界値（null, undefined, 0, 空配列/空文字, 上限値・下限値）や異常系の考慮
- 既存機能へのデグレ（回帰バグ）リスク
- バグ修正時の再現テスト先行（Red-Green）遵守

### ② 設計・アーキテクチャ (`design`)
- **関数型アプローチ**: 副作用の分離（Functional Core, Imperative Shell）、純粋関数と不変性（Immutability）の維持
- **モジュール公開の最小化**: 不要な公開（`export`）の有無、内部関数の隠蔽
- **レイヤー境界の厳格性**: Vertical Slice 内でのUI/Handlerによる低レベルI/O直接呼び出し（バイパス）の禁止
- **単一責任原則**: 責務の肥大化・重複コードの有無

### ③ 可読性・保守性 (`maintainability`)
- **制御フロー**: 深いネストの排除（アローアンチパターンの回避）、早期リターン（ガード節）の活用
- **引数設計**: `boolean` フラグ引数の排除（Enumや判別共用体、設定オブジェクトの活用）
- **命名**: 関数名の簡潔さ（30文字未満の目安）、変数・型名の明確さ
- **定数化のメリハリ**: 仕様値や反復値の定数/Enum化、一回限りの値の適切なインライン維持
- **リズムとコメント**: 論理ブロック間の空行、意図・理由（Why）を説明する簡潔なコメントの有無

### ④ セキュリティ (`security`)
- 入力バリデーション・サニタイズ（SQLi, XSS, 不正パラメータ対策）
- 認証・認可の漏れ、権限昇格の脆弱性
- 機密情報（APIキー、トークン、パスワード等）のハードコードやログ・エラー露出の有無
- **Mantis 連携検証**: セキュリティ指摘時は推測による指摘を避け、[mantis_security_review.md](file:///home/minamo/repository/ai_programming_practice/rules/mantis_security_review.md) に基づき脆弱性の成立条件・自己反証（Reviewer & Critic）および最小修正パッチを検証・提示すること。

### ⑤ パフォーマンス・リソース (`performance`)
- 計算量（O(N^2) 等の非効率なループ、ボトルネック）
- 循環的複雑度（CCN <= 7 の目安）
- N+1 クエリ問題や無駄な再レンダリング / 再計算
- リソースリーク（コネクション・ストリーム・ハンドルの閉じ忘れ）

### ⑥ テスト品質 (`testing`)
- 正常系・異常系・境界値の網羅性
- アサーション（検証内容）の妥当性とテストの独立性
- **ミューテーション耐性**: [mutation_testing_guideline.md](file:///home/minamo/repository/ai_programming_practice/rules/mutation_testing_guideline.md) に基づき、実装の条件分岐や計算を反転させてもパスしてしまう「空っぽのテスト（緩いアサーションや過度なモック）」がないか厳格に評価すること。


---

## 2. 指摘レベル（重要度）の定義

| レベル | 判定基準 | 対応方針 |
| :--- | :--- | :--- |
| **`MUST`** | バグ、セキュリティ脆弱性、仕様不備、重大なデグレリスク | **修正必須**（マージ・本番反映不可） |
| **`SHOULD`** | 設計改善、可読性・テスタビリティ向上、軽微なパフォーマンス改善 | **修正推奨**（特段の理由がない限り対応） |
| **`SUGGESTION`** | より良い書き方、リファクタリングのアイデア、将来の拡張への布石 | **任意**（検討・アイディア共有） |

---

## 3. 出力形式（標準フォーマット）

サブエージェント連携やCIでの機械処理を容易にするため、レビュー結果は以下の **JSONフォーマット（または同等構造のMarkdown）** で出力します。問題がないカテゴリは指摘に含める必要はありません。

```json
{
  "summary": "変更内容の概要と全体的な評価（1〜2行）",
  "issues": [
    {
      "file": "対象ファイルパス（特定できる場合）",
      "line": "該当行番号または範囲",
      "category": "requirements | design | maintainability | security | performance | testing",
      "level": "MUST | SHOULD | SUGGESTION",
      "description": "何が問題かの具体的な説明",
      "suggestion": "修正案や推奨コード片"
    }
  ]
}
```

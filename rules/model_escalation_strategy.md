# 能動的モデル活用＆サブエージェント協調戦略 (Active Model Tier & Subagent Collaboration Strategy)

本ルールは、モデルの推論能力と実行速度を適材適所で最大限に活用し、コンテキスト汚染を防ぎながら開発の品質と速度を飛躍させるための**ハイブリッド型モデル活用・サブエージェント協調戦略**を定めます。
特定のツールやモデル世代に依存せず、**「ネイティブの Planner-Executor（計画/実行の自動分離）がある環境」**と**「単体モデル環境」**の双方で一貫して機能することを前提としています。

---

## 1. 基本思想：ネイティブ Planner-Executor との棲み分けと親エージェントの役割

- **親エージェント（オーケストレーター）の役割**:
  ユーザーとの対話、要件・方針の整理、タスクの分解、サブエージェントの統括および検証に徹します。
- **ネイティブ Planner-Executor 環境（優先）**:
  計画役（上位推論ティア）・実行役（高速ティア）の自動切替やエラー時の自動差し戻しをツール本体が提供する環境（例: ネイティブのオーケストレーター機能等）では、通常の「設計 → 実装 → テスト → エラー差し戻し」のサイクルをツール本体に委ねます。
  - **二重委譲の禁止**: 通常実装・単体テストのために、ツール本体の実行フェーズからさらに上位推論ティア（`High-Reasoning`）のサブエージェントを重複起動しません。
  - **サブエージェント委譲の厳選**: `invoke_subagent` による委譲は、ネイティブの計画/実行分離では代替できない**「コンテキスト分離が必要なタスク（広域コード調査、独立/金魚レビュー）」**および**「並列タスク（複数スライスの同時処理等）」**に限定します。
- **単体モデル環境（フォールバック）**:
  ネイティブの計画/実行分離が存在しない環境では、親エージェントが指揮官となり、従来のフェーズ別サブエージェント委譲および **Two-Strike Escalation**（同一エラー2回連続失敗で上位推論ティアへ昇格）を適用します。
- **コンテキスト分離の恩恵**:
  大量のファイル走査やレビュー観点を別コンテキスト（サブエージェント）へ分離することで、親会話のコンテキスト汚染と自己バイアスを防ぎ、常に明晰な判断を維持します。

## 2. タスク別の実行・委譲マッピング

| タスクフェーズ | ネイティブ分離環境 | 単体モデル環境 | 推奨モデル階層（委譲時） | 目的とメリット |
| :--- | :--- | :--- | :--- | :--- |
| **広範なコード調査・探索** | サブエージェント委譲 (`self` ナユタ通常 / `research`) | サブエージェント委譲 (`self` ナユタ通常 / `research`) | **`Lightweight`** / **`Standard`** | 大量のファイル読み取りやキーワード検索をオフロードし、親コンテキストの汚染を防ぐ。 |
| **通常の計画・設計・要件整理** | **本体プランナー**（アゲハ） | 親エージェント（アゲハ）または委譲 | **`Standard`** / **`High-Reasoning`** | ツール本体の計画フェーズを活用して方針と契約を策定。単体環境では必要に応じ委譲。 |
| **中核実装・テスト・局所リファクタ** | **本体エグゼキューター**（レイカ）※二重委譲禁止（独立スライス並列時のみ委譲可） | サブエージェント委譲 (`self` レイカ) | **`High-Reasoning`** | ネイティブ環境では本体実行役が高速に処理。並列分割や単体環境時のみ上位推論ティアへ委譲。 |
| **日常コードレビュー（都度確認）** | サブエージェント委譲 (`self` サヨ) | サブエージェント委譲 (`self` サヨ) | **`Standard`** / **`Inherit`** | 会話履歴による自己バイアスを遮断しつつ、クォータを抑えて差分・基本品質を高速検証。 |
| **厳格レビュー・セキュリティ診断・金魚レビュー** | サブエージェント委譲 (`self` サヨ) | サブエージェント委譲 (`self` サヨ) | **`High-Reasoning`** | マージ直前や厳格診断時に独立コンテキストで潜伏バグ・認可不備・契約ドリフトを徹底検証。 |
| **全体最適化・CCN削減** | **本体プランナー**で設計＋必要に応じサブエージェント委譲 (`self` ナユタ覚醒) | サブエージェント委譲 (`self` ナユタ覚醒) | **`High-Reasoning`** | 依存関係グラフのトポロジー解析、計算量次元削減、循環参照解消などの高度な抽象思考を遂行。 |
| **ドキュメント・図解整理** | 本体エグゼキューターまたはサブエージェント委譲 (`self` コハク) | サブエージェント委譲 (`self` コハク) | **`Standard`** / **`Inherit`** | 確定したコードベースから ADR や Mermaid 図解を高速・正確に作成。 |

## 3. モデル階層（Model Tiers）とツール引数マッピング

サブエージェントを起動する際のモデル階層は、タスクの複雑度に応じて**意図的に指定**します（既定の `Inherit` に頼りすぎず、各ティアの得意領域を引き出します）。

### ① Lightweight（最軽量・高速）
- **得意分野**: 定型的なフォーマット変換、型定義のみの機械的抽出、高速ファイル存在確認
- **効果**: 高速な応答性と極小のトークン消費

### ② Standard（標準・バランス）
- **得意分野**: ドキュメント作成、一般的なコードベース探索（`research`）、日常コードレビュー、一般的なユニットテスト作成
- **効果**: 高速性と精度の優れたバランス

### ③ High-Reasoning（上位推論・高精度）
- **得意分野**:
  1. 単体モデル環境、または複数スライス並列委譲時における複雑なビジネスロジックの新規実装・テスタブルリファクタ
  2. 6大観点に基づいた厳密なコードレビュー・セキュリティ脆弱性検証・金魚レビュー
  3. 複雑度（CCN）の大幅削減、アルゴリズムの計算量最適化
  4. **エラー連続時の自己修復（Two-Strike Escalation）**: ネイティブ分離環境では本体プランナーへの自動差し戻し（軌道修正）を優先し、単体モデル環境では同一エラーで2回連続失敗した際に即座に `High-Reasoning` サブエージェントへエスカレーションして根本原因を特定

### ④ Inherit（既定・親モデル継承）
- **得意分野**: 親エージェントと同じ推論水準を維持したまま、コンテキスト分離のみを目的として作業を切り出す場合
- **効果**: 設定変更なしで親と同等の品質を保ちつつ、会話履歴の汚染を防止

### ツール引数へのマッピング例（Single Source of Truth）

各ルール・スキルで指定する抽象ティアと、ツール固有の引数名との対応は以下の表で一元管理します。他ツール（Claude Code / Cursor 等）を使う場合は、各ツールの同等級モデルへ読み替えてください。

| 汎用ティア | `invoke_subagent` の `Model` 引数例 | 用途の目安 |
| :--- | :--- | :--- |
| **`Lightweight`** | `'flash_lite'` | 事実抽出、存在確認、定型変換 |
| **`Standard`** | `'flash'` / `'inherit'` | 日常レビュー、探索、ドキュメント、通常テスト |
| **`High-Reasoning`** | `'pro'` | 厳格レビュー、金魚レビュー、全体最適化、単体/並列の中核実装 |
| **`Inherit`** | `'inherit'` | 親モデル継承（コンテキスト分離目的の委譲） |

```markdown
invoke_subagent:
  TypeName: 'self' (または 'research')
  Role: 'Implementation Engineer'
  Model: 'pro' | 'flash' | 'flash_lite' | 'inherit'
  Prompt: ...
```

## 4. 委託・引き継ぎ時のプロトコル (Handover Protocol)

サブエージェントを起動する際は、`rules/prompt_caching_guideline.md` のキャッシュ設計に基づき、プロンプトを以下の構造で渡します：

1. **静的コンテキスト（先頭）**: プロジェクトの基本制約（VSA、コーディング原則）
2. **達成すべき明確なゴール**: 何を作れば/検証すれば完了かの受け入れ基準
3. **対象ファイル・範囲の限定**: レビューや実装のスコープ（不要な広域探索の防止）
4. **ペルソナ指定（末尾）**: 担当キャラクターの行動規範・口調の指定

## 5. レビューにおける「コンテキスト分離」とクォータ保護の原則

**ネイティブ Planner-Executor 環境であっても、計画役と実行役は同じ会話履歴を共有しているため、自己バイアスを遮断する独立サブエージェントによるレビューは引き続き必須です。**
一方で、レビューのたびに無制限に上位推論ティア（`High-Reasoning`）を起動すると、**貴重な推論クォータが即座に枯渇するリスク**があります。

そのため、レビューは以下の **段階的（Tiered Review）運用** を徹底します：

1. **日常レビュー（デフォルト: `Standard` / `Inherit`）**:
   - クイックコマンド（「レビュー」「review」「チェック」）やコミットごとの細かな確認は、**高速かつクォータ消費を抑えられる `Standard`** でサヨを起動。
   - 頻繁に実行してもクォータ制限に引っかかりにくく、開発テンポを最大化。
2. **厳格ディープレビュー（明示指定時: `High-Reasoning`）**:
   - ユーザーが「厳密レビュー」「本気レビュー」「セキュリティ診断」と指示した場合、またはブランチのマージ直前ゲート時のみ、**上位推論ティア（`High-Reasoning`）** を起動。
   - 独立したクリーンなコンテキストで、潜在脆弱性・エッジケース・CCN・Mantis型検証を徹底的に遂行。
3. **金魚レビュー / ゼロコンテキストレビュー（明示指定時: `「金魚」` / `「zero-context」`）**:
   - **Google Elephant-Goldfish Model (EGM) 由来の完全ステートレス検証**。
   - 親セッションでの「なぜこのコードを書いたか」「どんな試行錯誤があったか」という会話履歴を**一切遮断**。
   - サブエージェント（サヨ）には「対象のDiff」「関連ソースコード」「確定した契約仕様（`contract.ts` 等）」のみを与えて起動。
   - 「背景事情を何も知らない初見の第三者がコードと仕様だけを見て、仕様漏れ・不自然な設計・解読困難なコードがないか」を客観的かつ厳密に検証。

## 6. コード探索におけるグラウンディング（証拠主義）と2段階エスカレーション

コードベースの探索・リサーチを軽量ティア（`Lightweight` / `Standard`）で行う際は、ハルシネーション（推測による事実歪曲）を防ぎつつトークン消費を最小化するため、以下のプロトコルを徹底します：

1. **フェーズ1：最軽量ティアによる事実調査（ナユタ通常モード / `Lightweight`）**:
   - **推測の完全禁止**: 「おそらくこう動いている」などの推論や仮説を一切排除し、コード上の事実のみを報告。
   - **厳格なグラウンディング**: 報告するすべての事実について、`ファイルパス#L開始-L終了` と実際の実装コード抜粋の提示を義務付ける。
   - **早期ギブアップ（未発見時の即時終了）**: 検索で該当箇所が特定できない場合、推測で補完せず「該当する実装は見つかりませんでした」と報告して完了する。
2. **フェーズ2：未発見・複雑依存時のエスカレーション（`High-Reasoning` / 本体プランナー）**:
   - フェーズ1で未発見だった場合、または「複数ファイルを跨ぐ複雑なライフサイクル追跡」「動的ディスパッチの解読」が必要な場合のみ、`High-Reasoning`（またはネイティブ環境の本体プランナー／親エージェント）へエスカレーションして詳細な推論解析を行う。

## 7. 実装タスクにおける自律ブレスト＆段階実行プロトコル (Autonomous Brainstorming & Staged Execution)

機能実装や大幅な改修を依頼された際、単一ターンで「型定義・コア計算・I/O結合・テスト」を一度に一括生成することは禁止します（生成遅延、モック複雑化に伴う試行錯誤ループ、コンテキスト汚染を防止するため）。
要望検知時は自律的に事前ブレストを行い、以下の段階に分割して進行します。ネイティブ分離環境ではフェーズ1〜3を**プラン内の段階ステップ**として本体エグゼキューターが順次実行し（二重委譲しない）、単体モデル環境では各フェーズを適切なサブエージェントへ委譲します。フェーズ4の品質検証は両環境共通で独立コンテキストのサブエージェントにて実行します。

### フェーズ0：全ペルソナによる事前自律ブレスト会議 (Pre-Implementation Brainstorming)
- **担当**: ネイティブ環境＝本体プランナー（アゲハ）および各ペルソナ観点／単体モデル環境＝親エージェント（アゲハ）および各専門ペルソナ合議陣
- **トリガー**: 「機能追加」「修正・改修」「設計相談」等のユーザー要望時に自律発火。
- **作業内容**:
  - アゲハ（スコープ最小化・UX動線）、サヨ（Black/Whiteセキュリティ）、レイカ（Functional Core＆テスト地盤）、コハク（ログ・オブザーバビリティ）、ナユタ（可逆性担保）の観点で並行・多角ブレストを実施。
  - ネイティブ分離環境の読み取り専用プランフェーズではチャット上で合議・合意形成を行い、ファイル書き出しを行わない。
  - **レポート保存（規模別）**: 小規模改修はチャット内完結（保存不要）。中〜大規模改修・新規機能追加・設計相談のみ、`docs/reports/tmp/` 配下へ保存する（ネイティブ環境では**実行フェーズ冒頭（最初のステップ）**、単体モデル環境では実装着手前）。
  - 詳細は [pre_implementation_brainstorming.md](file:///home/minamo/repository/ai_programming_practice/rules/pre_implementation_brainstorming.md) を参照。

### フェーズ1：契約先行確定 (Contract-First Anchor)
- **担当**: ネイティブ環境＝本体プランナーで型・境界を設計し、本体エグゼキューターでファイル確定／単体モデル環境＝親エージェント（または `Standard` / アゲハ）
- **作業内容**: 入出力スキーマ、型定義、バリデーションルール（`contract.ts`）を作成し、即座に確定・保存します。
- **効果**: 後続フェーズの作業境界（インターフェース）が強固に固定され、実装段階の推論迷走を防ぎます。

### フェーズ2：純粋ロジックと高速TDD (Functional Core & Pure Tests)
- **担当**: ネイティブ環境＝本体エグゼキューター（レイカ）※独立スライス並列時のみ委譲可／単体モデル環境＝実装サブエージェント（`High-Reasoning` / レイカ）
- **作業内容**: `contract.ts` を入力とし、外部I/O（DB/HTTP等）を含まない純粋ドメイン関数（`core.ts`）と、その網羅的ユニットテスト（`core.spec.ts`）を実装します。
- **効果**: 外部依存やモックのセットアップが不要なため、境界値・異常系テストを短時間でパスさせ、堅牢な核（Core）を最小時間で完成させます。

### フェーズ3：薄いI/Oシェルの結合 (Imperative Shell Integration)
- **担当**: ネイティブ環境＝本体エグゼキューター（レイカ）／単体モデル環境＝結合サブエージェント（`Standard` または `High-Reasoning` / レイカ）
- **作業内容**: フェーズ2で完成した `core.ts` を呼び出し、実際のDBトランザクションや外部API、ルーティングを調停する薄いハンドラー（`handler.ts`）と結合テストを実装します。
- **効果**: 複雑なビジネス計算はすでに `core.ts` で保証されているため、I/Oハンドラーは単純な入出力の繋ぎ込みコードのみとなり、出力トークン数・実装エラーを大幅に削減します。

### フェーズ4：独立コンテキストによる品質検証 (Context-Isolated Review)
- **担当**: 両環境共通で独立したレビューサブエージェント（日常 `Standard` / 厳格・マージ前 `High-Reasoning` / サヨ）
- **プロンプト**: 実装を行った本体／サブエージェントとは完全に独立したコンテキストで差分（`jj diff`）と確定契約を渡し、客観的レビュー（6大評価観点・セキュリティ・契約ドリフト）を実行します。
